# Counting/Ledger Mass-Validation Harness

Source: `src/lib/counting-engine/validation/`. This document explains what that harness proves, what it does not, how its independence from production is maintained, and how to run it at each scale. If this document and the code ever disagree, the code is authoritative.

## What this proves

Across a large, deterministically-generated number of simulated blackjack shoes/hands/CardEvents, the harness exercises the **real production path** — `createInvestigation`, `occupySeat`, `addCardToRound`, `undoTargetCard`/`redoTargetCard`, `advanceRound` (same-shoe and new-shoe), `markSeatEmpty`, `mutateRound`, and `calculateCountSnapshot` — and compares its output, after every operation, against a small, independently-written **reference model** (the "oracle," `oracle.ts`) that computes the same numbers a completely different way.

A passing run is evidence of the form:

> Passed *N* simulated hands / *M* CardEvents with zero detected mismatches against the independent reference model, across Hi-Lo, KO, Zen, and Omega II, including undo/redo, new-shoe boundaries, seat removal, hand-clearing, and reload-from-persistence.

That is the only claim a pass supports. **This is not a mathematical proof.** A randomized/property-style test suite, however large, samples a space — it does not exhaustively cover it. Treat a passing run the way you'd treat a large, well-designed fuzz test: strong evidence against the specific classes of bug it's built to catch, not a formal guarantee.

## What this does not prove

- **Not exhaustive.** The seeded generator produces realistic, varied sequences, but there are input shapes it may never (or rarely) generate — e.g. split-hand (`targetType: "split"`) CardEvents are not currently generated by the randomized simulator at all (only dealer/seat), and multi-seat linked-group betting mechanics aren't exercised here either. See "Known scope limitations" below.
- **Not a UI/React test.** The harness calls the repository/ledger layer (`lib/db/repositories/*`, `lib/counting-engine/*`) directly — it does not render `InvestigationContext`, `CardEntryPad`, `VoiceControl`, or any component. Those have their own test suites. This harness is specifically about numerical/ledger correctness at scale, not UI behavior.
- **Not a real-device persistence test.** "Reload" here means a fresh repository read (`getInvestigation`/`getCardEventsForShoe`) against the same in-process Dexie/fake-indexeddb instance, proving the read path doesn't depend on cached in-memory object references. It does not simulate an actual browser tab reload, app restart, or the service worker's own caching layer.
- **Not a performance/load test of the UI.** Timing numbers reported here are the harness's own repository-call throughput in a jsdom + fake-indexeddb test environment, not a measurement of real-device or real-IndexedDB performance.
- **Not proof the *oracle* is bug-free.** The oracle is small and hand-reviewable specifically so a human can audit it directly (see "Oracle independence" below) — but it is still hand-written code, not a formal specification. Two independent implementations agreeing on a huge number of cases is strong evidence, not a substitute for the tag tables in `docs/counting-systems.md` (the actual published-methodology source of truth) being correct.

### Known scope limitations (not yet covered by the randomized simulator)

- Split-hand (`targetType: "split"`) CardEvents.
- Player-group / linked-seat betting mechanics.
- Voice-entry parsing (`lib/voice/*`) — covered by its own dedicated test suite, not this harness.
- Practice-vs-production reset policy is covered by a small **deterministic** (non-randomized) scenario run once per harness invocation (`runPracticeVsProductionScenario` in `simulator.ts`), not scaled to thousands of cases — that policy is a discrete state-machine property, not a numerical one, and is separately covered exhaustively in `src/lib/db/repositories/investigations.test.ts`.

## Oracle independence

`oracle.ts`'s `ShoeOracle` computes "what the count should be" using a structurally different approach from production, not just a copy of it:

- **Production** (`calculateCounts.ts`) keeps every CardEvent ever written, dedupes by `id`, filters to `status === "active"`, sorts by `sequence`, and sums tag values over that filtered, ordered list.
- **The oracle** never touches ids, statuses, or sequence numbers. It keeps one integer counter per rank (incremented on add, decremented on undo) and one small LIFO stack per target (to know which rank a "undo last card for this target" should decrement). The running count for any system is always just `IRC(system) + Σ counter[rank] × tag[system][rank]` — a one-line reduction over ten counters.

The tag tables in `oracle.ts` are hand-transcribed from the published methodology recorded in `docs/counting-systems.md` (Thorp/Wong for Hi-Lo, Fuchs & Vancura for KO, Snyder for Zen, Carlson for Omega II) — not copied from `src/lib/counting-engine/countTags.ts`. If the two ever disagree, that is exactly the class of bug this harness exists to surface; the fix belongs in production code (after root-causing), never in the oracle just to make a run pass.

Two additional fixed, entirely hand-computed examples (worked out on paper from the same published tag tables, independent of both the oracle *and* production) live in `countingValidation.fixtures.test.ts`, alongside the pre-existing hand-verified "mandatory acceptance sequence" in `src/lib/db/repositories/cardEvents.test.ts` — random simulation supplements these, it does not replace them.

## Seeded reproducibility

All randomness flows through `rng.ts`'s `mulberry32(seed)` — a tiny, public-domain PRNG whose entire body is a few lines of bit arithmetic, chosen specifically so it can be read and verified by eye rather than trusted as a black box. The same `HarnessConfig.seed` always produces the exact same sequence of sessions, shoes, hands, cards, and undo/redo/workflow operations, forever, on any machine.

When a mismatch is found, the harness throws with a `MismatchDetail` containing the seed, investigation id, shoe number, round number, the exact op index and op that triggered the failure, the expected vs. actual values, and a compact `ReplayPayload` — the seed, deck count, counting system, and the full list of operations applied to *that one shoe* (never the whole run; a shoe's CardEvent ledger is already fully self-contained). Paste that payload into `EYEONPIT_REPLAY_PAYLOAD` and run `countingValidation.replay.test.ts` to reproduce the exact same failure in isolation, in milliseconds, through the identical `applyOp`/`verifySnapshot` code path that found it originally — see that file's header comment for the exact command.

## Running it

| Level | Command | Scale | Part of `npm test`? |
|---|---|---|---|
| SMOKE | `npm test` (runs automatically) | ~hundreds of CardEvents | Yes — always |
| STANDARD | `npm run validate:counting` | Thousands of hands (~2,000 hands / ~10,000 CardEvents at current config) | No — run deliberately, e.g. pre-release |
| STRESS | `npm run validate:counting:stress` | Tens of thousands+ hands / hundreds of thousands+ CardEvents | No — manual only, several minutes |

STANDARD and STRESS live in files ending `.massvalidate.ts` (not `.test.ts`), matched only by `vitest.validate.config.ts`'s own `include` glob — an ordinary `vitest run`/`npm test` never discovers or runs them, by construction, not by convention.

**Scaling beyond the current STRESS config** (per the "should reach 1,000,000+ CardEvents without an architecture change" requirement): raise `HarnessConfig.sessionCount`. The harness deliberately spreads load across many independent investigations rather than growing any single investigation very large — each investigation's own `rounds`/`eventLog` arrays otherwise grow without bound and each read-modify-write operation against it gets proportionally more expensive, so distributing across sessions is what keeps per-operation cost roughly constant as total scale grows. `HarnessConfig.checkEveryNEvents` is the other scale lever — it samples the (dominant-cost) per-card snapshot verification down to every Nth `addCard` at larger scales, while every `undo`/`redo`/`markSeatEmpty`/`clearHand` op and the once-per-round reload check remain fully, unconditionally verified regardless of sampling, and a `replayPayload()` run is never sampled — it always verifies every single op.

## Wording discipline

Never describe a passing run as "mathematically proven correct" or similar in product-facing language. Accurate phrasing: *"Passed N simulated hands/events with zero detected mismatches against the independent reference model."* This applies to this document, `docs/EYEONPIT_PRODUCT_SPEC.md`, commit messages, and anything shown to an operator or stakeholder.
